- Why did PATCH only need one field in the body?

- When would you choose PUT over PATCH in a real intern dashboard API?
    Use PUT when replacing the entire intern record with new data. Use PATCH when updating only specific fields, such as an intern's score, attendance, or role.

Why does returning 200 OK with { "error": "..." } break API consumers?
Answer:
    Returning 200 OK with an error message misleads API consumers into thinking the request was successful. Many frontend applications check the HTTP status code first. If they receive 200, they may try to process the response as valid data instead of handling it as an error, leading to incorrect behavior or application bugs.

Answer:
- Did the fake token cause a 401? Why not? (Think about what JSONPlaceholder does with the header.)
    No. JSONPlaceholder ignores the Authorization header because it is a mock API and does not perform authentication.
- In a real API, what would the server do with the Authorization header?
    The server would validate the token. If the token is valid, it would process the request; otherwise, it would return a 401 Unauthorized response.
- What is the difference between 401 and 403 in terms of the Authorization header?
    401 Unauthorized: The user is not authenticated or has provided an invalid/expired token.
    403 Forbidden: The user is authenticated, but does not have permission to access the requested resource.

Write a Comment
Is POST /projects/{id}/interns/{internId} a good endpoint for assigning an intern? Or should it be POST /interns/{id}/projects/{projectId}? What determines which is the "owner" resource?
Answer:
    Both endpoint styles are valid. The choice depends on which resource owns or manages the relationship.
    If projects are responsible for managing assigned interns, then:
    POST /projects/{projectId}/interns/{internId}
    is the better design.
    If interns are responsible for managing their assigned projects, then:
    POST /interns/{internId}/projects/{projectId}
    is more appropriate.
    The owner resource is determined by the application's business logic and how the relationship is managed.
